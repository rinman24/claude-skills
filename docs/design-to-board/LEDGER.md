## Session budget

Same as the port: under ~100K tokens per session, hard ceiling 120K, ~80K
of planned work per unit, one unit per session. Near the ceiling, stop,
update this ledger and write the next handoff.

## How sessions hand off

Handoffs are prompt files in `handoffs/`. To start the next session, open a
terminal in the worktree, start `claude`, and give it the handoff (paste it,
or send its path and ask it to follow it).

## Session protocol

Start:
1. Read the handoff prompt.
2. Fetch; if `origin/main` moved, merge it into the branch (never rebase a
   pushed branch).
3. Read this ledger and `LESSONS-LEARNED.md` (and the port's lessons the
   handoff names).
4. Mark the unit `in progress` below.

End:
1. Update item statuses and the session log.
2. Update [Rich's queue](#richs-queue) and record his rulings in
   [Decisions](#decisions).
3. Append lessons to `LESSONS-LEARNED.md`.
4. Write the next handoff from `handoffs/TEMPLATE.md`.
5. Commit and push the branch.
6. Tell Rich the handoff path and what's open in his queue.

### Exit-3 coverage (DB-D12, DB10)

`WRITE_FIXES[3]` says "re-run design-to-board, whose checks name what to do".
That holds only if every exit 3 squadra's `queue`/`withdraw` can raise
(`verb-contract.md`: `ClaimScopeRefusedError`, `QueueRefusedError`,
`TransitionRefusedError`, `DuplicateOriginError`, `UnknownOriginError`) is
seen by the re-run's read or checks, before any write. An empty cell is a gap.

| Exit-3 class | Verb | Case | What the re-run sees |
|---|---|---|---|
| `ClaimScopeRefusedError` | queue | first run, `--parent` out of scope | `--parent` check over `squadra board scope` (DB10) |
| `ClaimScopeRefusedError` | queue | later run, the map's parent out of scope | `_check_scope` over `Increment.in_claim_scope` (Juval's case 5); one predicate in squadra, so the item and the parent agree |
| `ClaimScopeRefusedError` | withdraw | item out of scope | `_check_scope` (case 5) |
| `QueueRefusedError` | queue | Origin already on the board, any Lifecycle | the translation table: only an absent Origin queues; the re-run reads the item and takes its cell (nothing, or live × WITHDRAWN's refusal) |
| `QueueRefusedError` | queue | a partial item carries the Origin and disagrees | the partial-item check over `squadra board partial-items` (DB11): squadra's `refuses` verdict on the Plan's queue fails as board state before any write, quoting its refusal |

| `UnknownOriginError` | withdraw | no Increment carries the Origin (removed by hand) | the translation table: withdrawn × ABSENT → nothing (DB-D9), so the re-run converges; a partial item carrying it gets DB11's `note ·` line (no queue names it), which blocks nothing |
